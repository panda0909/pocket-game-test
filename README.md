# 口袋股市守衛

以「口袋」品牌吉祥物為主角的股市主題隨機合成塔防遊戲，以 Godot 4.7 開發，可匯出為網頁版。
核心玩法參考《同盟塔防戰－並肩作戰》（英文名 Coop TD: Together）。

## 玩法

三隻吉祥物守護投資金庫，抵擋一波波沿著盤面軌道襲來的熊市入侵者。角色階級會沿用原始
吉祥物模型，逐階增加武器、護甲與能量效果；相關四階展示素材在
`assets/characters/tiers/`，戰場、敵人、特效、UI 與狀態素材在
`assets/generated/`。

- 按「買入守衛」花資金在 4×4 的盤面格上生成一隻**隨機種類**的一階守衛
- 把**兩隻同階守衛拖在一起**，合成為高一階、**種類也隨機**的守衛
- 每種基礎守衛都有獨立的待機圖與攻擊圖；開火時會短暫切換外觀並前撲
- 不同基礎守衛升到滿階後可融合成專用載具／搭配角色，解鎖新的攻擊型態
- 守衛自動攻擊軌道上的熊；熊抵達投資金庫會造成損失
- **每 20 秒自動推進下一波**，清不掉的敵人會和新的一波疊在一起
- 下方可發動全場 **EX 技能**（有冷卻），右側可切換 ×1／×2／×3 加速
- 生命歸零即結束，無限波次，記錄最高波數

棋盤有 16 格，中央交叉匯流點刻意留空；中央水平路徑上下各有兩列，沿著拉長的 T 字
上下對稱展開，角色之間有足夠空間辨識與拖曳。中後期必須在左右入口與匯流點之間
取捨高階輸出的位置，而不是把整個戰場塞成一面單位牆。

目前地圖是「左右雙入口 → 中央交叉匯流 → 下方金庫」的 T／Y 型防線。
兩條入口會交替生成敵人，左右區域也保留作為未來雙人分線合作的空間；
目前仍是單機原型，尚未接入網路同步。

拖曳規則：拖到空格是移動，拖到同階守衛是合成，拖到不同階守衛是交換位置。

敵人會依波次解鎖七種熊市形態：

| 熊市敵人 | 登場節奏 | 戰場辨識 |
|---|---|---|
| 熊 | 每波 | 基本熊市壓力 |
| 小熊 | 第 2 波起 | 高速、小體型 |
| 中熊 | 第 3 波起 | 中等血量與速度 |
| 大熊 | 第 4 波起 | 厚血、慢速 |
| 恐怖熊 | 第 6 波起 | 高威脅、會造成 2 點損失 |
| 殭屍熊 | 第 8 波起 | 最慢但耐久最高的常規熊 |
| Boss熊 | 每 5 波 | 黑金領袖造型，帶股市護盾 |

三種基礎守衛各有定位：

| 守衛 | 定位 | 特性 |
|---|---|---|
| 紅牛 | 單體重擊 | 傷害高、攻速慢，對高血量單體最有效率 |
| 橘壁虎 | 連射 | 攻速快、傷害低，對高速小熊好用 |
| 綠恐龍 | 範圍濺射 | 命中點半徑內全體受傷 |

滿階融合配方與定位：

| 滿階組合 | 融合角色 | 戰鬥定位 | EX 技能 |
|---|---|---|---|
| 紅牛 + 橘壁虎 | 雙人連擊 | 雙人搭配射擊，快速鎖定多個目標 | 對前方最多 8 隻敵人連射 |
| 紅牛 + 綠恐龍 | 市場戰車 | 戰車砲擊，範圍爆炸 | 大範圍高倍率砲擊 |
| 橘壁虎 + 綠恐龍 | 牛市飛機 | 飛機掃射，覆蓋全線 | 全場空襲 |

階級 1 到 12。基礎角色沿用原始模型，並以方形角標顯示階級；融合角色以「EX」
角標辨識。配色走「冷 → 暖 → 螢光 → 熔岩」的升溫路線。

## 開發

需要 Godot 4.7.2。開啟專案：

    /Users/hongming/Downloads/Godot.app/Contents/MacOS/Godot --path .

完整驗證（語法 → 單元測試 → 整合測試），改完程式跑這個：

    tools/verify_game.sh

只跑單元測試（**用這個腳本，不要直接呼叫 GUT**，原因見腳本開頭註解）：

    tools/run_tests.sh

不開視窗確認畫面：

    /Users/hongming/Downloads/Godot.app/Contents/MacOS/Godot --path . tools/capture.tscn -- /tmp/shot.png 300

擷取含角色階級與戰鬥素材的畫面：

    /Users/hongming/Downloads/Godot.app/Contents/MacOS/Godot --path . tools/capture.tscn -- /tmp/tiers.png 2000 tiers

重新產生敵人與金庫美術（詳見 [tools/README.md](tools/README.md)）：

    tools/.venv/bin/python tools/prepare_assets.py

## 匯出網頁版

    /Users/hongming/Downloads/Godot.app/Contents/MacOS/Godot --headless --path . --export-release "Web" build/web/index.html
    python3 -m http.server 8766 --directory build/web

然後開啟 <http://localhost:8766>。網頁版必須經由 HTTP 提供，直接開 `file://`
會因跨來源限制而失敗。

## 調整難度

所有旋鈕集中在兩個檔案，不必翻找散落各處的數值：

- `scripts/economy.gd` — 起始資金與生命、召喚費用曲線、擊殺與過關獎勵
- `scripts/wave_table.gd` — 每波熊市敵人組成、數量上限、生命值成長率

**調參請用模型，不要用引擎。** 這些曲線全是確定性公式，用 Python 直接
建模可以在幾秒內掃完整個參數空間；引擎在高倍速下受限於
`max_physics_steps_per_frame` 與 CPU，實測 `time_scale` 設 40 也只跑得動
約 1 倍速，跑一次到第 100 波要好幾分鐘。

目前的數值是這樣掃出來的（模型預估）：死亡約第 124 波、最高 8 階、
平均佔格 34/36。三條曲線互相牽動：

- **召喚費用成長（1.02）必須明顯低於收入成長（1.05／1.06）**，
  後期才買得起足夠的數量把棋盤鋪滿。兩者同速的話中期就卡死。
- **敵人生命成長（1.075）決定死亡波次**。玩家戰力大約隨波次的 1.38 次方
  成長（多項式），敵人是指數，交叉點就是終點。
- **早期壓力要留餘裕**。第一波若用掉超過六成的傷害預算，前幾波清不掉，
  漏怪複利消耗生命，死亡波次會從 124 直接崩到 9。目前設在 32%。

## 專案結構

| 路徑 | 內容 |
|---|---|
| `scripts/` | 遊戲規則的純類別（棋盤、合成、數值、經濟、波次、選敵），單元測試對象 |
| `scenes/` | 遊戲場景與其腳本；含左右雙入口的 T／Y 型戰場 |
| `assets/` | 原始吉祥物、角色階級裝備、戰場／敵人／特效／UI／狀態素材、字型與主題 |
| `test/unit/` | GUT 單元測試，共 71 個 |
| `tools/` | 資產產生、測試把關、整合測試、擷圖工具 |
| `docs/superpowers/` | 設計規格與實作計畫 |

## 架構重點

**規則與節點分離。** 所有遊戲規則放在 `scripts/` 下不繼承 `Node` 的類別裡，
節點只負責畫面與輸入。`Board` 是棋盤的唯一真相來源，`BoardView` 只把它畫出來。
六個純類別共 71 個單元測試，全部不需要建立場景樹。

**亂數可注入。** 合成與召喚的隨機性都透過外部傳入的 `RandomNumberGenerator`，
測試給固定種子即可穩定重現。隨機玩法若不先處理這件事，之後每個牽涉隨機的
測試都會變成間歇性失敗，而且事後補救要動到所有呼叫端。

**訊號單向往上。** `UnitView` 開火只管發訊號，不知道投射物怎麼生成；
`BoardView` 完成拖放只管發訊號，不知道規則怎麼判定。狀態改變集中在 `Main`。

## 這個專案踩到的坑

前作 Game1 的 [Godot 踩坑筆記](../Game1/docs/godot-踩坑筆記.md) 仍然適用
（背景 `ColorRect` 的 `mouse_filter`、拖曳要檢查按鍵遮罩、GUT 會靜默略過
壞掉的測試檔、驗證腳本不能用幀數當時間）。本專案另外遇到三個：

**`Path2D` 執行時不會自己繪製。** 它只在編輯器裡看得見。少了自訂的 `_draw()`，
玩家完全看不出軌道在哪、敵人從哪來——塔防最基本的資訊就沒了。
見 `scenes/track_view.gd`。

**`Input.parse_input_event()` 是非同步的。** 事件排進佇列，下一幀才派送。
自動化測試若假設「送出即生效」會偶發失敗；正確做法是等到狀態真的改變
（見 `tools/integration_check.gd` 的 `_drag_unit`）。

**中央大字會蓋住棋盤。** 遊戲中的提示要用棋盤上方的細長橫幅，
中央大字只留給標題與結束畫面。這種事只有實際截圖看過才會發現。
